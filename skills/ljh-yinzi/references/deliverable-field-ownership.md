# LJHskill 交付物字段所有权协议

本文件是仓库真源。实际消费者使用各自 `references/deliverable-field-ownership.md` 副本，副本由 `scripts/sync_field_ownership_protocol.py` 确定性同步。

## 一、协议目的

字段所有权回答三个问题：谁能形成标准字段，谁只能提出建议，问题应退回给谁确认。字段决策状态、证据状态和验证结果继续使用三轴状态协议。

标准字段至少包含：标准定位、标准人群和心智句。心智句是让团队和消费者记住「这个产品是谁、适合谁、凭什么值得选」的一句话。

### 买点清单的归属

买点清单是六要素里「买点」那一格的展开件，归 `/ljh-liuyaosu` 所有。清单至少写清每条买点的由头（故事、痛点、场景、情绪、其他）、对应的痛点或欲望、证据状态和字段决策状态。

- `/ljh-liuyaosu` 定清单，新增、合并或删除买点都要落回这里。
- `/ljh-maidian` 只评清单里的买点和主张，给出修改意见，不改清单。
- `/ljh-brief`、`/ljh-koc-brief`、`/ljh-duiqi`、`/ljh-xiegao`、`/ljh-jiaoben`、`/ljh-changjing`、`/ljh-lianming`、`/ljh-yinzi`、`/ljh-shangxiang` 只读引用。待确认买点写进初稿时保留括号和状态，不能写成已确认话术。

## 三、标准字段形成规则

1. `/ljh-xuanpin` 结论为「进入验证」后，才进入价值与定位阶段。
2. `/ljh-jiazhi` 只产价值候选。用户未确认的候选标「待确认」；工具提出的候选标「修改建议」。证据另标对应证据状态。
3. `/ljh-dingwei` 消费价值候选时保留候选属性，不得把候选直接写成事实。
4. `/ljh-dingwei` 产出的定位草案在确认前标「待确认」或「修改建议」。用户或有权负责人明确确认后，才记录为标准定位、标准人群和心智句。
5. 下游只把「已确认」标准字段作为固定输入。待确认内容可以进入初稿，但必须保留状态和缺口。
6. 买点清单按本节的归属流转。待确认买点进入初稿时写成括号或留空，进成稿前必须确认；`/ljh-xiegao` 不把待确认买点写进成稿。

## 四、下游发现问题时的处理

下游不能覆盖标准字段。发现问题时，同时输出：

| 项目 | 内容 |
|---|---|
| 原标准字段 | 原文、来源、当前状态 |
| 修改建议 | 建议的新写法或调整方向 |
| 理由 | 渠道适配、证据不足、表达冲突或结构断点 |
| 该回哪一步定（回退所有者） | 负责该字段的 Skill 或有权负责人 |
| 谁来拍板（确认动作） | 谁确认、确认什么、确认前如何使用 |

交给用户时用白话说，例如：「心智句我建议改成 X，理由是 Y。要改得回定位那一步（/ljh-dingwei）由品牌负责人拍板，拍板前照旧用原来那句。」

确认前，修改建议不能替换标准字段，也不能传给更下游作为已确认输入。

| 发现的问题 | 该回哪一步定 |

| 六要素定义或脚本结构问题 | `/ljh-liuyaosu`，涉及标准人群时再退回 `/ljh-dingwei` |
| 消费者语言、场景或画面翻译不清 | `/ljh-duiqi` |

## 六、证据与批准边界

1. 卖点评审通过，只代表本轮独特性和表达检验通过，不代表市场验证通过或合规批准。
2. 资质、检测来源、检测机构、授权和平台规则由品牌方、法务、检测机构或平台合规人员确认。
3. 页面、Brief 和脚本只能在证据核验范围内表达。画面演示不能替代检测、资质或市场验证。
4. 虚构故事、名人同款、贵族或古老配方等材料没有可追溯授权与来源时，证据状态标「无证据」，不得进入标准字段。
